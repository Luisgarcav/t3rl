# T3RL run kernel design

> For maintainers. Design for the first T3 Code integration increment of T3RL.

Status: approved design, not yet implemented
Date: 2026-08-24
Architecture context: [T3RL research lab architecture](../../internals/rl-lab.md)
Delivery context: [T3RL phased development plan](../../internals/rl-lab-roadmap.md)

## Purpose

Build the T3 Code side of the RL research lab — the run kernel — before any reinforcement learning
model exists. The kernel owns the contract vocabulary, the run lifecycle, worker process
supervision, durable run state, and artifact access. It is exercised end to end by a deterministic
fake worker that performs no learning.

This increment exists so that the plumbing and the science fail separately. When a real experiment
later fails to learn, the answer must never be "maybe the runner dropped a metric batch".

## Scope

### In scope

- `packages/contracts/src/rl.ts`: run vocabulary, lifecycle states, metric and artifact schemas,
  capability report, stable error codes.
- Six RPC methods on the existing WebSocket surface.
- `apps/server/src/rl/`: pure lifecycle, worker protocol parsing, process supervision, run store,
  artifact resolution.
- One SQLite migration adding three tables.
- One `AssetResource` variant so artifact bytes travel over the existing signed-URL path.
- `python/t3rl_worker/fake_worker.py`: a standard-library-only deterministic worker.
- A checked-in fake experiment definition that resolves to the fake worker, so `rl.startRun` exercises
  the real definition-to-manifest path rather than a special-cased test route.
- Focused tests, none of which require Python or a real subprocess except one gated smoke test.
- Corrections to the two existing proposal documents.

### Out of scope

No client UI. No reinforcement learning. No Python, framework, or accelerator installation. No GPU
or distributed execution. No multiple seeds. No reattachment to an orphaned worker after a server
restart. No agent-facing tools.

## Decisions

### D1: run lifecycle lives in a manager, not an event-sourced aggregate

A run is supervised the way `apps/server/src/terminal/Manager.ts` supervises a PTY: an in-memory
manager owns the process, and durable state is a row updated in place. The lifecycle itself is a
pure function in its own module, tested without a process, a database, or a clock.

The rejected alternative was a sibling event-sourced domain mirroring `apps/server/src/orchestration`
(decider, projector, reactors, receipts). Orchestration needs that machinery because a thread has
branching, checkpoints, and genuine concurrency between agent and user. A training run changes state
roughly six times in its life and has exactly one writer. Event sourcing here would be machinery
without a load to carry.

This decision supersedes the roadmap line "Run lifecycle facts are event-sourced". The upgrade path
is additive: adding a transition log later requires a new table, not a migration of existing data.

Also rejected: extending the orchestration aggregate so runs become thread events. That couples runs
to chat lifecycle, and the architecture document is explicit that a run must not be represented as a
conversation thread.

### D2: `rl.*` reuses orchestration scopes

`rl.*` read methods require `AuthOrchestrationReadScope`; `rl.*` mutating methods require
`AuthOrchestrationOperateScope`. No new scope literal is added.

Scopes are frozen per session at pairing time in `auth_sessions.scopes`, and the precedent in
`031_AuthAuthorizationScopes.ts` was a hard cutover that dropped every session rather than grant new
capabilities implicitly. Adding `rl:read` and `rl:operate` would therefore force every paired device
to re-pair. It would also buy no real isolation: a client that can dispatch an orchestration command
already causes arbitrary code to run on the server, which is strictly more privileged than starting
a training run.

Revisit if T3RL ever grants a credential that may read threads but must not spend compute.

### D3: metrics are never orchestration events

Metric batches are written to a dedicated table by the run store. The orchestration event log is not
reachable from the RL module. The constraint holds by construction rather than by review discipline.

### D4: artifacts live in server state, never in the user's project

Artifacts are written under `<stateDir>/rl/<runId>/`, a sibling of `attachments/` and `logs/`.
Nothing generated by a run lands in the project working tree, so a researcher's `git status` stays
clean and an agent working in that project never sees generated noise as source change.

### D5: artifact bytes use signed asset URLs, not the WebSocket

`AssetResource` in `packages/contracts/src/assets.ts` gains an `rl-artifact` variant alongside
`workspace-file`, `attachment`, and `project-favicon`. Artifacts then inherit the existing
expiring-token issuance in `apps/server/src/assets/AssetAccess.ts`.

Streaming a replay video over the WebSocket would be exactly the class of performance regression the
project audits for, and it would behave worst on the remote connections that matter most.

### D6: a quiet stream is never success

Terminal state is derived from the worker's `done` message together with process exit. Absence of
metrics is never interpreted as completion, and a stalled worker reaches a distinct terminal state
with its own error code.

### D7: active runs become `interrupted` on server start, not `failed`

`interrupted` is a distinct terminal state meaning "this was cut off and its outcome is unknown".
Reporting it as `failed` would fabricate a scientific claim about a run whose trajectory was never
observed.

## Architecture

### Module layout

```text
packages/contracts/src/rl.ts                          schemas, lifecycle states, error codes
packages/contracts/src/rpc.ts                         +6 entries in WS_METHODS
packages/contracts/src/assets.ts                      +1 AssetResource variant
apps/server/src/rl/Lifecycle.ts                       pure state machine, no I/O
apps/server/src/rl/WorkerProtocol.ts                  NDJSON decoding and validation
apps/server/src/rl/Manager.ts                         supervision, subscriber fanout
apps/server/src/rl/RunStore.ts                        SQLite reads and writes
apps/server/src/rl/Artifacts.ts                       confined artifact path resolution
apps/server/src/persistence/Migrations/041_RlRuns.ts  three tables
apps/server/src/config.ts                             +rlRunsDir in deriveServerPaths
apps/server/src/auth/RpcAuthorization.ts              scope mapping for the six methods
apps/server/src/ws.ts                                 one wiring block
python/t3rl_worker/fake_worker.py                     deterministic worker, stdlib only
```

`python/` is not a Node workspace package. Python framework types must never reach
`packages/contracts`.

### Ownership boundary

The browser never starts a process and never reads a file. A client sends a typed request; the
server validates it, resolves the experiment, spawns and supervises the worker, records lifecycle
changes, persists bounded telemetry, and hands back opaque identifiers. This holds identically for a
local desktop client and a remote browser, because execution never moves to the client.

## Run lifecycle

### States

```text
requested ──▶ preparing ──▶ running ──▶ cancelling
                                │            │
                                ▼            ▼
                          completed      cancelled
                             failed

any active state ──(server restart)──▶ interrupted
any active state ──────(error)───────▶ failed
```

- `requested` — accepted, nothing spawned yet.
- `preparing` — capability checks and manifest resolution; no training.
- `running` — worker sent `hello` and is producing output.
- `cancelling` — cancellation requested; the process tree is being stopped.
- `completed` — worker sent `done` with success and exited zero.
- `failed` — worker error, non-zero exit, protocol violation, or stall.
- `cancelled` — cancellation reached the process and it stopped.
- `interrupted` — the server restarted while the run was active.

`completed`, `failed`, `cancelled`, and `interrupted` are terminal and never transition again.
`failed` is reachable from every active state; `interrupted` is reachable from every active state on
server start.

**The first terminal fact wins.** If a worker sends `done` and exits on its own before a pending
cancellation reaches it, the run is `completed` or `failed` as the worker reported — not `cancelled`.
Recording `cancelled` for a run that actually finished would discard a real result.

### Shape

```
transition(state, event, now) → Accepted(nextState) | Rejected(reason)
```

Pure. Time is a parameter, never read inside. Invalid transitions are rejected explicitly and
observably rather than silently ignored, which is what makes the rejection path testable.

### Idempotency

- Starting a run returns a fresh `RlRunId` per accepted request. There is no implicit deduplication;
  a caller that retries deliberately gets a second run, which is correct for research.
- Cancelling an already-terminal run succeeds without effect and returns the terminal state.
- Cancelling twice while `cancelling` is a no-op.

## Contracts

### Types in `rl.ts`

| Type | Contents |
|---|---|
| `RlRunId` | opaque server-generated identifier; clients never mint one |
| `RlExperimentRef` | project-relative path to a version-controlled experiment definition |
| `RlResolvedManifest` | effective configuration, seed, source revision and dirty-worktree evidence, Python executable and environment fingerprint, runner id and version, worker protocol version, instrumentation level, relevant hardware |
| `RlRunLifecycle` | tagged union of the states above, carrying error code and message on `failed` |
| `RlRunSummary` | compact row for listing and reconnection |
| `RlMetricBatch` | `{ step, wallClockMs, values }`; bounded key count and key length |
| `RlArtifactMetadata` | `{ artifactId, kind, bytes, contentType, producedAt }`; the id is opaque and never a path |
| `RlCapabilityReport` | available runners, and for each unavailable one an actionable failure |

`RlMetricBatch.values` maps a metric name to `number | null`. `null` means **not captured**. A
synthetic zero is forbidden: in reinforcement learning a zero loss and an unrecorded loss are
opposite claims, and conflating them makes charts lie.

### Bounds

Every schema that crosses the wire is bounded at the contract layer, following the pattern already
used in `packages/contracts/src/terminal.ts`: maximum metric keys per batch, maximum key length,
maximum artifact count per run, maximum error message length.

### RPC methods

| Method | Scope | Behavior |
|---|---|---|
| `rl.capabilities` | read | report runners and actionable setup failures; never installs anything |
| `rl.listRuns` | read | run summaries for a project, newest first |
| `rl.getRun` | read | manifest, summary, artifact metadata |
| `rl.startRun` | operate | validate, resolve manifest, spawn; returns the run id |
| `rl.cancelRun` | operate | request cancellation; returns immediately |
| `rl.subscribeRun` | read | snapshot then live lifecycle and metric batches |

`rl.subscribeRun` follows the snapshot-then-live shape of `terminalAttach` in
`apps/server/src/ws.ts:2046`, so a client that reconnects rebuilds current state without replaying
the run and without duplicating it.

## Worker protocol

Versioned NDJSON on the worker's stdout, one JSON object per line.

| Message | When | Notes |
|---|---|---|
| `hello` | first, within a startup timeout | carries protocol version, runner id, runner version |
| `manifest` | once, after `hello` | runner-resolved defaults, merged into the stored manifest |
| `metrics` | repeatedly | a batch; rate-limited server side |
| `artifact` | as produced | kind plus a path relative to the run directory |
| `error` | any time | stable code plus message |
| `done` | last | success or failure |

A missing or late `hello`, an unknown message type, an incompatible protocol version, malformed
JSON, or an oversized line all fail the run deterministically with a distinct error code.

`stderr` is captured into a bounded ring buffer and retained as the run log artifact. It is never
parsed for meaning.

### Backpressure

At most two metric batches per second reach subscribers and the store. Excess batches coalesce;
they are never queued without bound. No queue, ring buffer, log, or artifact path in this design is
unbounded.

### Cancellation

The server terminates the process tree using the PID it captured at spawn: `SIGTERM`, then `SIGKILL`
after a grace period. Process discovery by name, path, or worktree pattern is forbidden — the
training process will carry the worktree path in its argv exactly as the developer's own agent does,
and pattern matching would kill the wrong thing.

## Persistence

Migration `041_RlRuns.ts` follows the idempotent style of `033_ProjectionThreadsSettled.ts`.

- **`rl_runs`** — one row per run: run id, project id, experiment id, state, resolved manifest JSON,
  error code and message, requested/started/ended timestamps, worker PID, last message timestamp.
  Index on `(project_id, requested_at DESC)`.
- **`rl_run_metrics`** — `(run_id, seq, step, wall_clock_ms, values_json)`, indexed by
  `(run_id, seq)`. Deliberately its own table; see D3.
- **`rl_run_artifacts`** — opaque `artifact_id` to run-relative path, plus kind, byte size, content
  type, and produced timestamp.

Deleting a run deletes its rows and its directory under `<stateDir>/rl/`. Retention policy and
quotas are deferred, but the directory layout is chosen so that a future sweeper needs no index.

## Artifacts and security

`Artifacts.ts` mirrors `resolveAttachmentRelativePath` in `apps/server/src/attachmentPaths.ts:12`:
normalize, reject `..` segments, null bytes, and absolute paths, resolve, then assert the result
still sits under the run root. A client-supplied identifier can never escape its run and can never
resolve an absolute host path.

The worker's environment is an explicit allowlist. Server credentials are not copied wholesale into
the training process.

## Failure behavior

Each of these reaches a durable terminal state with a distinct, stable error code: Python or runner
unavailable, missing or late `hello`, incompatible protocol version, malformed message, oversized
message, worker stall, worker exception, unexpected exit without `done`, and server restart while
active.

Capability failures are reported before a run is attempted, with a remedy string. The lab never
attempts to install Python, native packages, or framework wheels.

## Verification

`apps/server/src/processRunner.ts:292` takes an injectable `ChildProcessSpawner`, so manager tests
drive a fake spawner that emits lines on demand. No manager test spawns a real process, requires
Python, or waits on wall-clock time. **A test that needs a timeout to pass is wrong.**

- `Lifecycle.test.ts` — every valid transition, and explicit rejection of every invalid one.
- `WorkerProtocol.test.ts` — fixtures for valid streams, malformed JSON, unknown type, incompatible
  version, oversized line, missing `hello`.
- `Manager.test.ts` — success, worker-reported failure, cancellation mid-run, stall, unexpected exit
  without `done`, metric coalescing under burst, subscriber fanout, snapshot-then-live correctness.
- `Artifacts.test.ts` — traversal, absolute path, null byte, and symlink escape attempts.
- `RunStore.test.ts` — round trips, restart sweep marking active runs `interrupted`, deletion.
- `041_RlRuns.test.ts` — migration idempotency.
- One separately gated smoke test that runs the real `fake_worker.py` under `python3` to prove the
  spawn, discovery, and NDJSON path work outside the fake spawner.

Verification runs targeted: the touched test files plus lint and typecheck for the changed scope.
Repo-wide checks are CI's job.

## The fake worker

`python/t3rl_worker/fake_worker.py` imports only the standard library and performs no learning.
Scenario flags: `success`, `fail`, `malformed`, `stall`, `exit` (dies without `done`),
`ignore-cancel` (proves the `SIGKILL` escalation), and `bad-protocol`.

Deterministic by construction: identical metric values, artifact bytes, and message ordering on
every run, so a diff in test output means a real behavior change.

## What this unlocks

With the kernel green, a real experiment becomes a definition file plus a runner that speaks the
protocol. The drift-car environment and its verifiable reward function can then be designed as a
research question rather than as a plumbing question, and a failure to learn will point at the
reward, not the transport.
